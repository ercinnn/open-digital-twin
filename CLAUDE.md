# CLAUDE.md - Open Digital Twin Platform

Open-source digital twin for ships / shipyards and buildings. CAD (`.step` `.ifc` `.ocx` `.obj` `.stl`) -> Python BOM + Headless Blender `.glb` -> Supabase (data, storage, realtime) -> Flutter app with an embedded Three.js viewer.

## 1. Status
The demo shipyard (project 3) has no ships in the GLB (`CTX_SHIP_*` removed): ship projects are built IN THE APP and exported into `seed.sql` (currently NB-1001, see below). Hand-written seed: 20 yard areas, 6 cranes, organization / shifts / assignments, HSE zones and incidents, 2 crane maintenance bookings, general stock; no punch items, no trace events.
- Goal: build a ship project step by step IN THE APP; add the missing app features one step at a time. Step 1: Production "New hull". Step 2: Production "Blocks" (`blocks_dialog.dart`): block list per hull from the catalogue `blockTypeCatalog` (`block_entities.dart`, 29 types in 9 zones), default codes by `BlockBreakdown` (zone series 1xx bottom ... 9xx other, `P` / `S` suffix for port / starboard, e.g. `DB-101`, `SS-201P`), stored as `components` (`hull_structure`, `NODE_<HULL>_BLOCK_<CODE>`, metadata `hull_no`, `block_no`, `block_type`, `side`, `erection_sequence`). Step 3: 3D of the blocks without Blender: `HullBlockGeometry` (`hull_block_geometry.dart`) shapes each block from hull L / B (depth `metadata.depth_m` or estimated), type, side and number (blocks of one type split the type's hull region aft -> fore in block number order) at its erected position on the berth (dry dock if the hull location is `NODE_A17_DRY_DOCK`; several hulls in tandem) plus a ghost `CTX_<HULL>_HULL_ENVELOPE`; viewer command `set_procedural` builds the meshes (GLB meshes with the same id win). Camera menu has one view per hull with blocks. Step 4: block-level draft schedule (`BlockSchedule` in `draft_schedule.dart`, Production Plan > Draft schedule): for a hull with blocks every block gets its shop chain (cutting, bending for curved types, panel, assembly, coating, pre-outfitting for engine room / superstructure / thruster / stern; days by type and weight, back-scheduled to be ready 4 days before erection, shortened when keel laying is close to steel cutting) and an erection slot (erection sequence spread over keel laying -> launching); launching ... delivery stay hull rows. Hulls with rows can schedule blocks added later (slotted into the full sequence). Step 5: crane lifts (`LiftPlan` in `lift_plan.dart`, Resources "Plan lifts" > "Block erection"): one `planned` lift booking per block erection row without one (`activity_id` = the row) on the crane whose `metadata.location` is the erection area, smallest capacity >= block weight, first free window 07:00-17:00 of the erection days (existing bookings and the past skipped); blocks without weight are booked without a load (no capacity check).
- Step 6: block weights (Blocks dialog "Edit names / weights", `BlockEdit` in `block_entities.dart`): name and `weight_kg` of existing blocks (the code stays, it is the mesh id); saving runs `LiftPlan.syncLoads`, which brings every `planned`, future erection lift of the hull in line with the block weights (`load_t`, window `liftDuration`, same start if it still fits the day, else first free window; a too-heavy block moves to the smallest crane at the area that carries it; confirmed / past lifts are only reported) and is applied in order, one update per lift (a failed run can be resumed by saving again). Stage days scale with weight (`BlockSchedule.daysOf`) only for rows drafted afterwards. Default weights: `BlockWeights` (`block_weights.dart`) estimates the hull steel (Watson-Gilfillan from L, B, D = `metadata.depth_m` or estimated like the 3D, T from DWT and ship type text) and shares it by zone / type fractions (`typeShares`, present types take over absent ones up to `maxZoneGrowth`) and equally per block; in the dialog an empty weight field shows the estimate (≈ grey) and saves it, "Use estimates for all" clears typed weights.
- Step 7 (done: 7a-7c, each block's materials, inspections and permits; all three are tabs of `BlockDialog`, opened by tapping a block chip in the Blocks dialog). Step 7a: block material reservations (migration 012 `material_reservations`: item, block `component_id`, hull, quantity, `needed_by`, status `reserved` -> `issued`; one open reservation per item and block). The DB keeps `material_items.quantity_block_reserved` = sum of open reservations (`quantity_reserved` stays the manual part; free = on hand - both, negative = shortage, allowed); issuing checks stock on hand, lowers it and writes a trace event `issued` with the block. App: `BlockDialog` tab Materials (`BlockMaterialsPanel`: reserve / change / issue / delete); Materials "Reserve steel" -> `SteelReservationPlan` (`block_materials.dart`): block weight (or estimate) -> 80 % plates (item per steel grade of the block type, `A` for superstructure) / 20 % profiles, +8 % allowance, needed by = first schedule row of the block; blocks that already have a reservation of an item are skipped.
Step 7b: ITP inspections per block (migration 013: `quality_inspections.activity_id` = schedule row of the ITP point, `hold_point`; trigger: a row cannot get `actual_end` while one of its hold points is not `pass` / `conditional`). `InspectionPlan.fromSchedule` links every point to its row, marks hold points (block dimensional + UT, block coating, pre-launching survey, pressure test, HAT, docking survey), skips (row, type) pairs already planned (so the Quality draft can be repeated for rows added later) and can be limited to one block. `BlockDialog` tab Inspections (`BlockInspectionsPanel`: list, record result, "Plan ITP" for the block, single inspection); chip icons in the Blocks dialog: red = failed inspection, orange hand = open hold point, box = open reservations.
Step 7c: permits per block (migration 015: `work_permits.activity_id` = schedule row the permit covers; trigger `_check_work_permit_link`: row of the same project and block, hull from the block; a `lifting` permit of an erection row only becomes `active` while a planned / confirmed / running crane lift of that row overlaps the permit window). `PermitPlan` (`permit_plan.dart`): permits per stage (workshop stages cutting / bending / panel none; assembly: confined space for tank blocks `tankTypes`; coating: painting; pre-outfitting: hot work; erection: lifting + hot work + work at height; + confined space for tanks) for the block's running rows and rows starting within 7 days, covered by a current permit of the same row and type; `suggest` prefills the request (lifting: the booked lift window; else the day shift 07:00, 10 h). Block dialog tab Permits (`BlockPermitsPanel`): needs with "Request" (prefilled `NewPermitDialog`, zone warnings also of the row's area) and the block's permits (tap: approve / activate / close).

## 3. Rules (critical)
- **DB names:** English `snake_case` for tables, columns, RPCs, buckets.
- **Mesh ids:** every GLB node keeps its `mesh_node_id` = `components.mesh_node_id`; format `NODE_<UPPER_SNAKE>` (<= 60 chars, `cad_parser.sanitize_node_id`), stored as node name and `extras.mesh_node_id`. Ingest fails (HTTP 500) if a BOM id is missing in the GLB.
- **Context geometry** `CTX_*`: not in the BOM, ghosted and not pickable (`extras.ctx_opacity` 0..1, default 0.16, >= 0.99 opaque).
- **Hull blocks** `NODE_<HULL>_BLOCK_*` are modelled at their erected position; the viewer moves them to the area of their running / last schedule row, ghosts them during cutting / bending / panel and hides them before the first activity. The erected position belongs to the hull's site at the scene date (`HullPositions`: berth / dock, quay after launching, none at sea / after delivery). Only block-level schedule rows (`component_id` = block) move blocks; the app's draft schedule is per block when the hull has blocks.
- **Secrets:** `SUPABASE_SERVICE_ROLE_KEY` only in the root `.env`. `frontend/.env` is bundled into the app: public values only. Never commit either.
- **Access:** `anon` / `authenticated` read only. Writes need an editor (row in `public.app_editors`, RPC `is_editor()`); the UI shows write controls only if `isEditorProvider`. Add one: `insert into public.app_editors (user_id) select id from auth.users where email = '<email>';`
- **Backend auth:** all endpoints except `/health` need `Authorization: Bearer <editor access token>` (`app/auth.py`). `AUTH_REQUIRED=false` only for local experiments.
- **Status values:** `normal` green, `in_progress` blue, `warning` orange, `alert` pulsing red. Simulators never overwrite `in_progress`.
- **Business rules live in the database** (constraints / triggers); the app shows their error messages (`ShipyardRepositoryImpl._rethrow`).

## 4. Pipeline
1. Upload CAD to bucket `raw-cad-files` (`<project_id>/<file>`, `projects.raw_file_url`).
2. App starts `POST /api/v1/ingest/{project_id}/jobs` (202) and polls `GET /api/v1/ingest/jobs/{job_id}` (one job at a time, in memory). `cad_parser.py` -> BOM upsert into `components` on `(project_id, mesh_node_id)`; Blender `convert_to_glb.py` -> `processed-models/<project_id>/model.glb`, `projects.glb_model_url`. Without Blender: unoptimized trimesh GLB + warning.
3. Click on a mesh -> `node_selected` -> details, documents, telemetry. Realtime on `components.status` recolors meshes.
4. Sensor simulation runs in the DB (migration 004): pg_cron `odt_simulate_telemetry` (1/min, thresholds from `metric_profiles`), `odt_telemetry_retention` (4 days), `odt_cron_history_cleanup`. Button = RPC `simulate_telemetry` (editors); "Live" stops after 10 min. `metric_profiles` MUST mirror `telemetry_simulator.PROFILES` (backend test) - change both in a new migration.

## 5. Shipyard module (migrations 005-020, demo project 3)
- Shown for projects with rows in `hulls` or `departments` (`shipyardEnabledProvider`), so an empty yard can create its first hull. Tables use `_odt_secure_table()` (public read, editor write); realtime on `production_activities`, `resource_bookings`, `punch_items`, `work_permits`.
- DB rules: booking overlap per (resource, slot) = exclusion constraint (23P01); load > `metadata.swl_t` / `lifting_capacity_t` rejected; crane `alert` suspends / resumes its bookings (back to the interrupted status, 020); confirmed bookings start / finish with their window, planned ones never start by themselves (pg_cron, 020); hot work / confined space need O2 19.5-23.5 % and LEL < 10 % to become `active`; inspections with a measured value get pass / fail from the acceptance band; launching needs all erection rows of the hull finished and then moves the hull to the quay (016); commissioning needs all afloat outfitting rows finished, one work package per hull (017); a work package needs its material issued, its lifting permits a booked quay lift (018); sea trials / delivery need their required checklist items done or waived, delivery also finished sea trials, and moves the hull out of the yard (019).
- Editors can create / edit in the app: hulls (Production "New hull", Dashboard card tap), hull blocks (Production "Blocks": add from the catalogue, edit name / weight, delete; tap a block for its material reservations, inspections and permits), schedule rows (Production "Plan": draft from milestones, outfitting work packages, add, edit plan, delete), stock items (Materials "New item", tap to edit), block steel reservations (Materials "Reserve steel"), work package material (Materials "Reserve outfitting"; Gantt package bar > "Materials, ITP & permits"), sea trial / delivery checklists (Gantt bar > "Checklist"), inspections (Quality "Plan": single or ITP draft from the schedule; record result, delete), permits (HSE "Request permit", then approve / activate), bookings (Resources "New booking", "Plan lifts": block erection or outfitting at the quay; tap to confirm / finish / cancel).
- Pure Dart logic in `features/shipyard/domain/services/` (placements, Gantt, KPIs, `block_breakdown.dart`, `hull_block_geometry.dart`, `hull_position.dart`, `draft_schedule.dart`, `outfitting_packages.dart`, `outfitting_lifts.dart`, `lift_plan.dart`, `block_weights.dart`, `block_materials.dart`, `inspection_plan.dart`, `permit_plan.dart`) and draft classes with `validationErrors()` in `domain/entities/`, all unit tested.
- Viewer commands: `set_placements`, `set_overlay` (color mode `overlay`), `set_markers` (event `marker_selected`, ids `punch:|qi:|permit:|incident:<uuid>`), `set_highlights`, `set_labels`, `set_hidden`, `focus_nodes`, `set_procedural` (event `scene_nodes`). `ThreeViewerController.detach(sender)` ignores stale senders.
- Every `NODE_*` referenced by the operations seed must exist in the demo components (backend test). Seed dates are relative to `current_date` / the current hour.

## 6. Gotchas
- PostgREST `.order()` defaults to DESCENDING: always pass `ascending:`.
- Web: after a deploy the browser may keep running the cached old app (Ctrl+F5); data written by an old version can miss new columns.
- Web: the viewer iframe swallows clicks under Flutter dialogs / menus; `three_viewport_web.dart` makes it click-through while another route covers the page. Keep it when touching the viewport.
- Web: horizontal lists need explicit mouse support (scrollbar, drag, wheel), see `_HullStrip` in `dashboard_tab.dart`.
- `DropdownButtonFormField.initialValue` is read once: give it a `ValueKey` when the value changes programmatically.
- Riverpod 3: family notifiers get their argument via the constructor; use `ref.listenManual(..., fireImmediately: true)` in `initState`; check `mounted` before using `ref` after an `await`.
- Do not run `dart format` on existing folders (the code is not dart-format clean); format only new files.
- trimesh 5 merges OBJ objects unless `split_objects=True`; `ifcopenshell` needs the MSVC 2015-2022 x64 runtime. file_picker 13: static `FilePicker.pickFiles`, read with `readAsBytes()`.
- Supabase CLI runs `seed.sql` only once; after editing it use `scripts.reset_demo_data --publish` (resets ALL demo projects, incl. data entered in the app).

- Never put the service-role key on devices; planned: per-device keys via an Edge Function. Aggregate at the gateway (1-min averages); the simulator alone writes ~130k rows/day (free plan: 500 MB).
